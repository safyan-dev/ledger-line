# Taste — Command Code user preferences
- Keeps controllers/endpoints thin: they accept the request and delegate to an application service that owns validation, idempotency, state updates, and orchestration. Confidence: 0.75
- Prefers rich domain entities over anemic models, using in-process/in-memory domain events for cross-module notification; explicitly does not want Kafka/RabbitMQ introduced. Confidence: 0.7
- Wants gap analysis separated from implementation: when asking for missing-goals/audit work, expects the agent to stop at findings and not start coding until told. Confidence: 0.55
- Wants local database infrastructure to include a GUI SQL client (pgAdmin alongside Postgres in Docker Compose) so they can browse tables and run ad-hoc SQL themselves, not just through the API. Confidence: 0.55
- Distrusts permissive domain rules that let suspicious data through: rejects "an order can have multiple payments" as justification, and expects a payment that would duplicate/overpay an already-settled order to be captured for manual review instead of auto-matched or explained away as correct behavior. Confidence: 0.6
- Expects new product capabilities to be validated against real-world business practice before coding ("proceed to implement, first verify it if it's real business use case?") — wants a justification grounded in how the industry actually handles the flow, not just a plausible-sounding domain rule. Confidence: 0.6
- Explicitly dictates the PostgreSQL identifier naming convention for tables and columns (asked for camel_case, accepted snake_case) instead of letting EF Core defaults stand; expects schema naming to be a stated, enforced decision. Confidence: 0.6
- Enforces module ownership of business rules: a domain rule must live in its owning module (e.g. matching rules belong to the reconciliation module), and ingress/webhook handlers must not duplicate or pre-empt that logic. Confidence: 0.55
- Expects out-of-order data to be retained and recoverable rather than rejected: a payment arriving before its order should be stored as unmatched, stay visible in the review queue, and be matchable once the order exists. Confidence: 0.55
- Verifies results himself by running the whole suite and pasting the raw pass/fail output, so a change touching a shared script/config must be validated against all scenarios (not just the one edited) before it is reported as working. Confidence: 0.5
- Judges completion by end-to-end business scenarios, not module-level checks: supplies flows (happy payment, duplicate delivery, amount mismatch, unknown order, retry after failure, late-arriving order) and expects each run to assert the persisted rows, the derived dashboard/reporting totals, and that no duplicate business side effect occurred. Confidence: 0.6
- Uses the internal order id as the provider event id for its own webhook flows. Confidence: 0.5
- Specifies the full contract for inbound webhooks/events: acknowledge fast (explicit millisecond budget), never surface processing errors to the provider, keep retries idempotent by replaying the same event id, gate on signature verification before anything is stored, and persist/observe every expected rejection (unknown type, missing ids, malformed payload, conflicts) instead of throwing it away. Confidence: 0.65
